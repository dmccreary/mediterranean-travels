    How We Built This Site¶

    This book was built with Claude Code and a set of open-source intelligent-textbook skills. This page lists the steps in the order we did them. For each step it gives the prompt we used, the skill and the skill version, and a rough estimate of how long the step took.

    The estimates come from three sources:

    • The commit history of this site's GitHub repository (115 commits).
    • The session logs in the repository's logs/ folder, which record the skill version, start and end times, and results of the larger steps.
    • The time stamps on the prompts in 39 Claude Code sessions.

    All times are US Central time. Several sessions often ran at the same time, so the step times overlap and do not add up to the total elapsed time.

    Before and After the Trip¶

    Only the first step was done before we left. Before the trip, the site held an empty book frame, a course description, and an interactive map of the cruise route. That was 3 of the 115 commits.

    Everything else, over 95 percent of the work, was done after we came home. This was on purpose. Our shared Google Photos album holds 1,465 photos and videos, and each one records the date, time, and GPS position where it was taken. That photo stream is a record of what we actually did. It shows which day we were at Delphi, that we went to Cape Sounion, and which sites on the plan we skipped. So the book describes the trip we took, not only the trip we planned.

    Our Photos Never Went to GitHub¶

    The book is public, but our photo album is not. The original photos and videos were never checked into GitHub. They stayed on the author's MacBook the whole time.

    Where it lives In GitHub?
    Google Takeout export: 1,453 original photos (mostly HEIC) and 15 videos, 4.4 GB data/takeout/ on the MacBook Never
    Takeout zip file Downloads folder, deleted after unzipping Never
    Contact sheets (thumbnails Claude used to choose photos) data/contact-sheets/ on the MacBook Never
    121 small web copies of the chosen photos, with GPS data removed docs/chapters/*/img/ Yes
    Text files of file names, dates, places, labels, and scores data/*.csv, data/*.jsonl Yes

    Three things kept the originals out:

    1. A .gitignore file came first. When we asked Claude to unzip the export, we also asked for a .gitignore so it could not be added to the repository. The file data/.gitignore lists takeout/, *.zip, and contact-sheets/, so git does not see those folders at all.

    2. We asked Claude to confirm it. Before any photo work started, the prompt was:

      Please confirm that the photos and videos will NOT be added to GitHub.

    3. Only small copies are published. scripts/export_web_photos.py makes a small JPEG of each chosen photo and drops its metadata, including the GPS position, before it goes into the book.

    Anyone can check this. This command lists every photo or video file, or Takeout file, that was ever committed to any branch of the repository. It prints nothing:

    git log --all --name-only --format= | grep -iE '\.(heic|mov|mp4)$|takeout/'

    Claude worked with the originals without sending them anywhere. The labels came from Apple's Vision framework running on the laptop, the places came from the GPS data in Takeout's JSON files, and Claude only looked at one contact sheet per chapter (see Step 9).

    Models Used¶

    • Claude Sonnet 5.5 was the default model for most of the work.
    • Claude Opus 5.5 was used to generate the MicroSims and the posters, which need more careful code and layout.
    • The session logs for the learning graph, the chapter design, and the color themes (all on November 24) record that Opus 5.5 was used for those steps.
    • OpenAI image models made every AI-generated image, including the graphic-novel story panels and the poster illustrations. Claude wrote a description of each image into the book's files, both on the laptop and on GitHub. The author then used the ChatGPT desktop app and simply told it to render the images from those descriptions. No prompts were copied and pasted by hand. The high-quality poster images were critical to the posters: the interactive labels only work if the picture underneath is accurate and clear.

    Which OpenAI image model?

    We believe the images were made with OpenAI Images 2.6, which OpenAI released for Codex and ChatGPT on November 4, 2026. Its API versions are GPT‑Image‑2.6 Flare (gpt-image-2.6-flare) and GPT‑Image‑2.6 Sunburst (gpt-image-2.6-sunburst). We could not find any metadata in the image files that proves this. It is what OpenAI said were its current versions when the images were made.

    Step 1: Build the Frame and the Cruise Map (Before the Trip)¶

    When: the evening of November 10 and the morning of November 11. Time: about 1 hour. Skills: book-installer v1.0.4, microsim-utils v1.0.

    We created the GitHub repository and set up an empty MkDocs Material book. Then we turned an existing HTML map of the cruise into a standard MicroSim, and wrote a course description from the cruise itinerary.

    /book-installer init

    Refactor the HTML program in docs/sims/viking-cruise-map.html into a standard
MicroSim format using the /microsim-utils standardization guide, and add it to
the MicroSims section of the mkdocs.yml nav.

    This is not actually a textbook, but a travel guide of things to notice on our
trip. I am a big fan of the history of civilization, culture, cuisine, and
trying to have deep empathy for the people in the places on our trip. Please
update the course description to reflect this. Here are the details of our
travel plans: [the cruise itinerary pasted from the cruise-agency site]

    The result was the Viking Cruise Map and the first version of the course description. Then we packed.

    Step 2: Connect the Google Photos Album¶

    When: November 24, 8:27 AM, then 12:56 to 1:35 PM. Time: about 30 minutes of work, plus about 30 minutes waiting for Google. Skill: none (a custom Python script).

    Google Photos does not have an open API for reading a shared album, so we used Google Takeout. Takeout exports the original photos plus a JSON file for each one with its date, time, and GPS position. Claude wrote scripts/google_photos_takeout.py to read the export, and a profiling script to summarize it.

    Google really let us down here

    The author was very unhappy to learn that there is no simple API for reading the photo metadata from a shared album. All we needed was the date, time, and GPS position of each photo. That is a few megabytes of data.

    Google's Photos API has never returned GPS positions. Google strips the location from the photos it hands to apps, and says it does this on purpose. Since March 31, 2025, the API cannot even read an album unless the same app uploaded its photos. So the only way to get the metadata was to download the full 4.4 GB Takeout export of every original photo and video. This was slow, and it wasted time, bandwidth, and disk space. Google really has let us down. See Google's own notice: Updates to the Google Photos APIs.

    Add a Google Photos connector to this project.

    The download is in the Downloads folder as a zip file. Uncompress it and do
basic data profiling of this data. Put the results in the book's data
directory, but do not check the photo files into GitHub. Add a .gitignore so
they are not added to the repository.

    Please confirm that the photos and videos will NOT be added to GitHub.

    Delete the zip in Downloads.

    The export held 1,465 photos and videos (4.4 GB). They stay in data/takeout/ on the MacBook, which data/.gitignore keeps out of the repository. See Our Photos Never Went to GitHub.

    Step 9: Pick the Trip Photos¶

    When: November 24, 1:36 to 3:25 PM. Time: about 2 hours, most of it the computer labeling photos. Skill: none (custom scripts).

    We wanted our own photos in the chapters. But sending 1,465 photos to an AI model to look at would use a very large number of tokens. So we asked for a cheaper way:

    I would like to enhance the chapter content with a small selection of sample
photos. But to do this you would have to analyze the photos for their content,
and that would take a LOT of tokens. Is there a low-token way to select the
photos that should be included?

    Claude built a pipeline that runs mostly on the laptop and uses no AI tokens until the last step:

    1. scripts/photo_labels.swift uses Apple's on-device Vision framework to label each photo (for example "ruins," "mosque," or "harbor") and give it a quality score.
    2. scripts/select_chapter_photos.py uses each photo's GPS position to find the nearest landmark, and so the chapter it belongs to. It drops screenshots, signs, and photos where a face fills the frame, and keeps the best photo from each burst.
    3. The top photos for each chapter are tiled into one numbered "contact sheet" image. Claude reviews a whole chapter's choices by looking at one image instead of dozens.
    4. scripts/export_web_photos.py makes small web copies of the chosen photos and removes their GPS data.
    Longer chapters can have up to 10 photos that are unique.

    For each of the photos, add a credit to the photo caption.

    Add the photo rules to CONTENT-GENERATION-GUIDE.md, including the photo
caption rules.

    The book now uses 121 of our photos. The counts by place are on the Trip Photo Metrics page.

    Lessons for Your Own Trip Book¶

    • Set up before, write after. A small amount of work before the trip (the frame, the itinerary, and a map) is enough. The photo stream records what you really did, so most of the book is better written afterward.
    • Keep the photos private and use their data. Add the .gitignore before you unzip the export. The original photos and videos stay on your own computer. Only small web copies, with the GPS removed, go into the book.
    • Avoid sending every photo to the AI. On-device labels, GPS matching, and contact sheets let Claude choose photos for the cost of one image per chapter.
    • Write a few chapters, then fix the guide. Checking chapters 1 to 3 and updating CONTENT-GENERATION-GUIDE.md before writing the other 18 kept the same mistakes from being repeated 18 times.
    • Let long jobs run on their own. The MicroSims took about 7 hours, but needed only three short prompts and one review the next morning.
